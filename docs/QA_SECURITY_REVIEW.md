## Security and authorization review

- All six public application tables have RLS enabled.
- Patient journal and mood policies scope access to `patient_id = auth.uid()`; therapist SELECT policies require an active relationship and the corresponding patient-granted permission.
- Homework creation requires an active relationship with `can_manage_homework = true`. Patient homework updates are protected by the patient ownership policy and column-level grants: authenticated users can update `status`, but not `title`, `instructions`, `patient_id`, or `therapist_id`. This is the intended completion-only capability; do not broaden it.
- Appointment creation requires an active relationship with `can_manage_appointments = true`.
- Connection requests are restricted to the authenticated patient, pending status, all permissions false, and an account whose profile role is therapist.
- The two patient consent/revoke RPCs are intentionally `SECURITY DEFINER` because patients need to update their own access row while direct access-table updates are not exposed. Both functions use an empty search path, schema-qualify table references, and constrain the target row to `patient_id = auth.uid()` plus the expected pending/active state. The advisor confirms authenticated execution but no anon execution. Retain this design only with negative cross-patient tests; do not remove the identity check or grant execution to anon.
- Supabase Auth leaked-password protection is currently disabled. Enable it in the Supabase Auth password-security settings after an authorized project owner reviews the user-experience impact. It was not changed during this review.
- Performance advisor warnings report separate permissive SELECT policies for patient and therapist access on appointments, homework, journal, and mood. These represent distinct patient-owner and consented-therapist paths. Consider consolidating each pair into a single carefully parenthesized OR policy only after regression tests prove both paths and denial cases remain correct.
- The journal/mood indexes are currently unused on this small, near-empty database. Keep them until representative workload measurements justify removal.
- Never put the Supabase service-role key, Resend key, or cron secret in frontend code, repository files, browser storage, or logs. The frontend uses only the publishable key.

## Required synthetic-account test procedure

1. Create a second account using a dedicated synthetic test mailbox, then confirm its email. Do not use real patient data.
2. Obtain that account's Auth UUID from the Supabase Auth user list. Verify its profile defaults to patient.
3. Change only that synthetic profile's role to `therapist` using an authorized project-owner operation; never change the existing patient account's role.
4. Sign in as the patient and request the therapist connection using the synthetic therapist UUID. Confirm that the request is pending and every permission is false.
5. Approve only homework management from the patient session. Verify the therapist can see the relationship but cannot read journal/mood or manage appointments.
6. Assign a dummy homework item from the therapist session. Verify it appears to the patient, then complete it from the patient session. Verify the database status changes to `completed`.
7. Attempt negative cases: therapist without consent cannot insert homework; therapist cannot read journal/mood without those permissions; a different patient cannot read or update the test patient's rows; patient cannot change homework title or owner fields.
8. Test appointment creation only with a synthetic patient/therapist pair and a future dummy slot. Keep `reminder_enabled = false` during functional tests unless the owner explicitly approves a controlled email test to a verified test mailbox. Never send reminders to real users.
9. Verify that no service-role or provider secrets are present in built frontend assets.
